# Implementation Plan: M6.2 — Token-Budget Characterization (Production Latency Budgets Across `max_tokens` Axis)

**Branch**: `027-m6-2-token-budget` | **Date**: 2026-05-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/027-m6-2-token-budget/spec.md`

## Summary

M6.2 lifts `max_tokens` from M6.1.x's fixed cap (10 for embed, 50 for chat_stream — held constant as the protocol-isolation control) to a **six-point measurement axis `{10, 50, 256, 512, 1024, 2048}`** under each (cell × cohort) pair, producing per-cohort p50/p95/p99 wall-clock latency budgets across realistic production response lengths. The operator question shifts from "which protocol wins under fixed engine work" (M6.1.3's framing) to **"what does the per-cohort latency budget look like at 256/512/1024/2048 tokens, and at what `max_tokens` does protocol choice stop mattering?"**.

**Three user stories** (from [spec.md](./spec.md)):

1. **Per-cohort latency budget table** (P1, US1) — the headline deliverable. 6 cells × 4 cohorts × 6 caps = 144 measurement points; `wall_p50_ms` / `wall_p95_ms` / `wall_p99_ms` per row; inherited 5-segment engine-cost decomposition per row; null-anchor validation at `max_tokens=10/50` against M6.1.3's published CIs.
2. **Protocol-crossover threshold** (P2, US2) — per-cell `crossover_max_tokens` derived from the **symmetric mean-in-CI rule** (spec round-1 Q3, pinned inline). The reporter emits a "Protocol crossover threshold" markdown section identifying the smallest `max_tokens` at which the M6.1.3-winning cohort's `wall_p50_ms` falls inside the second-place cohort's `[wall_p50_ms ± CI_half_width]` (or vice versa).
3. **KV-cache pressure observation** (P3, US3) — characterizes the `c=8 × max_tokens=2048` regime via the **wall-clock-ratio inference** (spec round-3 Q3, pinned at threshold 2.2) computed unconditionally from existing latency budget measurements, plus best-effort capture of `engine_kv_cache_used_fraction` if vLLM exposes it via gRPC trailing metadata.

**Four structural exogenous-confound controls** (spec round-4, new in M6.2 because the 20-40h wall-clock budget exposes the sweep to time-of-day variance the M6.1.x ~75-min sweeps never saw):

- **FR-030 cohort-innermost block iteration** — for each `(cell, max_tokens)` tuple the orchestrator runs all `n` RPCs for cohort 1, then cohort 2, then 3, then 4, BEFORE advancing to the next tuple. All four cohorts at a given tuple share a ~30 min – 4 h time window, so between-cohort `wall_p50_ms` comparisons (the headline) are time-of-day-controlled at the granularity that matters.
- **FR-031 intra-sweep anchor re-measurement at every 4h mark** — lightweight `chat_stream × c=1 × max_tokens=10` block (`n=20`) per cohort at each 4-hour mark (aligned with FR-009 `network_paths` cadence; ~25 min cumulative overhead, < 1.5% of wall-clock). Reporter aggregates per-cohort `anchor_latency_trajectory` (8-10 snapshots in publish mode) and fires `latency_drift_warning` per cohort whose `max_minus_min_wall_p50_ms` exceeds the M6.1.3 published CI half-width.
- **FR-032 per-block UTC timestamps + iteration-discipline verification** — every `(cell, cohort, max_tokens)` row carries additive `block_start_utc` / `block_end_utc` ISO-8601 fields; the markdown's "Sweep wall-clock timeline" subsection renders the iteration sequence so operators can visually confirm FR-030 discipline; `run_meta.iteration_discipline_verified: bool` machine-checks that every `(cell, max_tokens)` tuple's 4 cohort blocks ran contiguously.
- **FR-033 in-window retry once, no end-of-sweep retry pass** — each block MAY retry ONCE if the first attempt fails (transient gRPC error, dispatch timeout, single-RPC OOM that doesn't crash the engine) BEFORE the orchestrator advances past the current `(cell, max_tokens)` tuple; retries AFTER the tuple closes are FORBIDDEN (would violate FR-030 by running in a different time-of-day window than sibling cohorts). Per-row `retry_attempted: bool` field persists for operator visibility.

**Four sweep-level integrity warning channels** (publish-blocking-eligible: operator decides whether to publish or rerun):

- FR-014: ≥ 3 of 48 anchor cells outside M6.1.3's published CI → null-anchor cross-milestone drift header.
- FR-029: ≥ 3 cells with `failed_<reason>` markers OR any single `(cell, max_tokens)` point with all 4 cohorts failed → failure-summary header.
- FR-009 / SC-010: consecutive `network_paths` snapshots reveal a cohort CSP / region change → cohort-CSP-mismatch warning.
- FR-031 / SC-016: ≥ 2 of 4 cohorts carry `latency_drift_warning = true` → intra-sweep latency-drift header.

Plus one **soft diagnostic warning** (NOT publish-blocking-eligible, informational only):

- FR-032 / SC-017: `iteration_discipline_verified = false` → iteration-discipline header. Indicates that FR-030's cohort-innermost rule was broken; operator inspects the wall-clock timeline subsection to diagnose.

**Implementation discipline (FR-028 + spec round-1 Q1)**: M6.2 is produced by **copying the M6.1.3 `m6_1_3_*` module family into an `m6_2_*` namespace and refactoring only the deltas the `max_tokens` axis requires**. Regenerating the measurement path from scratch is FORBIDDEN — instrumentation drift would invalidate the null-anchor comparison against M6.1.3's published CIs (FR-012 / FR-013) and recreate exactly the methodological confound that triggered M6.1.1's creation. Mirrors M6.1.3's "Copy-Then-Refactor" methodology (plan §254-288), now established as the M6.x project-wide convention per FR-027.

**Round-3 deferral (spec round-2 Q1 + FR-004)**: Publish-mode `n` selection (`{50, 100}` or adaptive per axis) and the wall-clock + Modal-spend caps (FR-021 / FR-023) are deferred to a **future clarify round 3**, gated on the validate-sweep within-cohort stddev at `chat_stream c=1 × max_tokens=2048`. The publish-mode orchestrator MUST refuse `--m6_2` invocation if the `n` config knob is unset. The validate sweep runs at `n=20` pinned on the 3-point axis subset `{10, 50, 2048}` (~2.3-2.5 h wall-clock, ~$4 Modal spend).

**No `--m6_2-asymmetric-prompts` flag** (FR-008, spec round-3 Q1): symmetric prompts are on by default and the only mode shipped via CLI in M6.2; the flag name is a forward-reference for a future milestone (e.g., M6.2.1) if asymmetric diagnostic re-runs ever become necessary.

**Two published artifacts** (distinct paths per FR-015):

- `docs/benchmarks/m6_2-token-budget.{md,json}` — canonical M6.2 publish artifact from `--m6_2`.
- `docs/benchmarks/m6_2-token-budget-validate.{md,json}` — validate sibling from `--m6_2-validate`.

**M6.1.3 forward-pointing annotation** (FR-019): single leading `> **Note**:` line in M6.1.3's published markdown body pointing forward to M6.2 for the realistic-generation-length budget. Reciprocal "Method / Background" cross-reference in M6.2's body. Mirrors the M6.1.1 → M6.1.3 minimal-touch convention established in M6.1.3's FR-031.

The split is intentional — the crossover and anchor-trajectory modules each carry pure functions that are easier to unit-test in isolation than as part of a larger orchestrator module.

## Implementation Methodology: Copy-Then-Refactor Pattern (project-wide convention from M6.1.3)

Every new M6.2 module that has an M6.1.3 (or M6.1.2 / M6.1.1) analog MUST be implemented as a **copy-then-refactor**, NOT a from-scratch reimplementation. The implementation diff is exactly the refactor — small, focused, reviewable — and inherits every prior-milestone fix automatically. This methodology is the M6.1.3-plan-§254 project-wide convention propagated to M6.2 per spec FR-028 + spec round-1 Q1.

### What this methodology does NOT apply to

**Modifications to existing files** (`__main__.py`) are **in-place additive edits**, not copy-then-refactor. The existing constraint stands: additions are strictly new argparse wiring; no behavioral change to existing mode-flag handlers.

**Unit tests for net-new modules** (`test_m6_2_iteration_order.py`, `test_m6_2_anchor_trajectory.py`, `test_m6_2_crossover.py`, `test_m6_2_kv_pressure.py`, `test_m6_2_retry_policy.py`, `test_m6_2_null_anchor.py`, `test_m6_2_artifact_schema.py`, `test_m6_2_cli.py`) are written against the contracts and data model directly — there's no prior-milestone test to copy because the surfaces being tested (cohort-innermost iteration, intra-sweep anchor trajectory, symmetric mean-in-CI crossover, wall-clock-ratio KV-pressure inference, in-window retry policy, M6.1.3 null-anchor comparison, M6.2 artifact schema, M6.2 CLI) are net-new to M6.2.

### Trade-off

Code duplication across the `m6_1_1_*` / `m6_1_2_*` / `m6_1_3_*` / `m6_2_*` families accumulates with each milestone. This is the explicit cost of the parallel-module pattern + the prior-milestone freeze rule — a shared module would break historical re-runnability. The duplication is bounded by the milestone count (4 sibling families after M6.2; 5 by M7); future consolidation may extract truly-shared logic into helpers (the M6.1.3 `symmetric_prompts.py` case is the first such extraction).
