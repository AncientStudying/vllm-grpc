- Q: Label-precedence tie-breaking when multiple classifier rules fire on the same cell — strict decision-tree order, highest-share-wins (with or without dominance margin), or ranked list? → A: **Highest-share-wins with a 5-percentage-point dominance margin; near-ties produce a compound label `multi_factor_<top>_<runner_up>`**. When two or more attribution labels clear their thresholds (per FR-008's per-rule fractions of total `engine_ttft_ms` spread), the label whose driving segment carries the highest share wins iff that share exceeds the runner-up's by ≥ 5 percentage points. If the top two are within 5 points of each other, the cell receives `multi_factor_<top>_<runner_up>` (e.g., `multi_factor_proxy_egress_engine_compute`) and the per-cell narrative enumerates the contributing segments verbatim. `inconclusive_high_variance` (FR-026) still wins as the outer label when it fires — the highest-share-wins / compound logic determines the *inner* label that becomes a parenthetical. The 5-percentage-point margin is the spec-level constant; the per-rule dominance thresholds (the `~40%`-of-total-spread floors per FR-008 / `seg_*_dominated` rules) remain `/speckit-plan` deliverables. Compound labels follow the precedent set by `multi_factor_<a>_<b>` ordering: top-share segment first, runner-up second, alphabetical within tied pairs.
- Q: Multi-run H1 verdict aggregation — per-run + majority vote, worst-case wins, single-run only, or pool-then-verdict? → A: **Pool-then-verdict: aggregate all 5 runs' per-RPC audit data into one per-cohort distribution per cell (n_rpcs = 5 × 50 = 250 per cohort), then apply FR-016's H1 / H2 / rejection criterion once on the pooled distribution**. Single published verdict per cell drives the spec-decision recommendation (FR-017 / FR-018). The 5 runs are samples from the same population (same deploy, same seed, same n, no teardown between runs per FR-022), so pooling yields a more powerful test with tighter per-cohort mean estimates and a more honest cross-cohort stddev than per-run-then-aggregate. Per-run verdicts MAY be computed and rendered in a diagnostic appendix table for transparency (operator-readable, not load-bearing for downstream spec assumptions). The published verdict line in the headline audit section is the single pooled-data verdict. For validate-mode (`--m6_1_3-validate`, single run) the pooled n is just 50 — same criterion applies, just smaller sample.

### User Story 1 - Close the c=4 / c=8 `inconclusive` Verdicts With Attributed Proxy-Edge Labels (Priority: P1)

A future operator (or M6.1.1 cohort-comparison reader) needs to know whether the unattributed budget in M6.1.1's two `inconclusive` `chat_stream` cells at `c=4` (~17 ms of 26 ms total spread, 64%) and `c=8` (~5 ms of 13 ms total spread, 37%) lives on the proxy-ingress side (frontend's `pre_engine_ns` → vLLM's `arrival_time`) or the proxy-egress side (vLLM's `first_token_ts` → frontend's `first_chunk_ns`). The spike's read-only investigation (2026-05-17, `docs/spikes/m6-1-roadmap-additions/03-proxy-edge-instrumentation-gap.md`) confirmed feasibility: vLLM's engine-core monotonic timestamps use `time.monotonic()`, the engine runs in-process with our frontend servicer, so the clocks are comparable — no upstream vLLM contribution required. Without bisection, those cells stay `inconclusive` and the M6.1.1 cohort-comparison verdicts are silently load-bearing on uncharacterized budget; with bisection, each cell collapses to one of seven attributable labels (the existing five plus `proxy_ingress_dominated` and `proxy_egress_dominated`).

**Why this priority**: This is the only structural change that *closes* M6.1.1's two open Phase 2 verdicts — the audit (Story 2) characterizes the c=1 finding's root-cause but doesn't help c=4 / c=8; the multi-run variance (Story 3) bounds uncertainty but doesn't reduce the unattributed-budget fraction. Without Story 1, the bundle still produces useful data but the two highest-uncertainty cells remain unattributed, which is the headline gap motivating M6.1.3. It carries the most novel implementation risk and the most direct user-visible value, so it gets P1.

**Independent Test**: Can be fully tested by running the smoke-equivalent validation sweep (per FR-039) against a fresh Modal deploy and confirming the resulting artifact JSON contains per-cell, per-cohort `seg_ingress_ms` and `seg_egress_ms` fields (alongside the inherited `seg_ab_ms`, `seg_queue_ms`, `seg_prefill_ms`), AND that the classifier's per-cell label-set covers seven possible verdicts. A reader can compute `seg_ingress_ms + seg_egress_ms` per cell × cohort and confirm the previously-unattributed budget is now within `seg_*` segments summing to within sample-noise of `engine_ttft_ms`. Re-classification of M6.1.1's `inconclusive` c=4 / c=8 cells using the new probes' data is the headline outcome.

**Acceptance Scenarios**:

1. **Given** the operator launches an M6.1.3 sweep (`--m6_1_3` for the publish run or `--m6_1_3-validate` for the smoke-equivalent wiring check), **When** each streaming-path RPC executes (chat_stream cohorts; embed is unary so the gap doesn't apply), **Then** the frontend servicer captures `m6_1_1_t_pre_engine_wall_ns = time.time_ns()` alongside the existing `pre_engine_ns` and `m6_1_1_t_first_chunk_mono_ns = time.monotonic_ns()` alongside the existing `first_chunk_ns`, and emits both via gRPC trailing metadata (for gRPC cohorts) or the SSE / JSON terminal event (for REST cohorts).
2. **Given** a sweep produces per-RPC timing rows, **When** the M6.1.1-expansion classifier extractor reads them, **Then** the extractor computes `seg_ingress_ms = (engine_arrival_ns − pre_engine_wall_ns) × 1e-6` and `seg_egress_ms = (first_chunk_mono_ns − engine_first_token_ns) × 1e-6` per RPC; both values MUST be `≥ 0`. Negative values fire a wire-format sanity-check assertion that surfaces the clock-source mismatch.
3. **Given** the per-cell aggregator runs, **When** it aggregates segments across RPCs, **Then** the `PerSegmentAggregate` structure (and the per-cohort row in the published artifact) contains `seg_ingress_ms` and `seg_egress_ms` columns in addition to the inherited segment columns.
4. **Given** a per-cell `PerSegmentAggregate` is fed to the classifier, **When** the classifier evaluates its decision tree, **Then** the cell receives one of seven possible labels: the five inherited from M6.1.1 (`channel_dependent_batching`, `engine_compute_variation`, `queue_dependent_batching`, `frontend_arrival_jitter`, `inconclusive`) plus the two new `proxy_ingress_dominated` (where `seg_ingress_ms` carries the dominant per-cohort spread) and `proxy_egress_dominated` (where `seg_egress_ms` does). When Story 3's multi-run variance machinery is also active, the same cell may receive `inconclusive_high_variance` per Story 3's FR-026.
5. **Given** the M6.1.1 `chat_stream` c=4 cell that previously classified `inconclusive` with ~17 ms unattributed, **When** the M6.1.3 sweep re-runs the same cell with the new probes, **Then** the per-cohort `seg_ingress_ms + seg_egress_ms` sums account for the previously-unattributed budget (within sample noise), and the cell receives one of the two new `proxy_*_dominated` labels OR the inherited `channel_dependent_batching` / `engine_compute_variation` label if the bisection reveals the budget lived in the existing segments (the probes both bisect and act as a sanity check on the original instrumentation).
6. **Given** an M6.1.1-aware (pre-M6.1.3) reader / consumer parses the artifact JSON, **When** it reads a per-cell row with the new `seg_ingress_ms` / `seg_egress_ms` fields, **Then** the unknown fields are ignored silently — strict-superset schema evolution, no `schema_version` bump (stays at `m6_1_1.v1`), mirroring M6.1.1's own additive expansion precedent.
7. **Given** any embed (unary) cell, **When** the sweep iterates that cell, **Then** the proxy-edge probes do NOT emit `seg_ingress_ms` / `seg_egress_ms` fields for those rows (the gap is a streaming-only phenomenon — `Complete` is unary, there is no first-chunk-vs-engine-emit delta to bisect). The extractor treats absent fields as `null` rather than firing the negative-value assertion.

### User Story 2 - Identify the Root-Cause of `chat_stream c=1`'s Reproducible `engine_compute_variation` (Priority: P2)

A future reader of M6.1.1's published artifact needs to know *why* `default_grpc` spent ~5 ms more in post-schedule engine compute than `rest_https_edge` or `tuned_grpc_multiplexed` at `chat_stream c=1` — a finding that's reproducible across runs (between-run |Δ| 0.37 ms vs within-run spread 5.8 ms, per spike #6's two-run analysis) but not explainable from the existing instrumentation. The spike's investigation (`docs/spikes/m6-1-roadmap-additions/04-engine-compute-variation-rootcause.md`) enumerated six hypotheses (H1 prompt-content drift, H2 encoding drift, H3 KV-cache prefix-reuse, H4 cohort-order warmup bias, H5 channel-config side effect, H6 HTTPS-Edge cold-path — eliminated) and flagged a load-bearing context finding: M5.2 had prompt-symmetry enforcement (`m5_2_symmetry.py`); M6 / M6.1 / M6.1.1 dropped it. **H1 is the leading candidate** — if cohorts cycle through deterministically-seeded prompts in a different order, each cohort sees a different prompt distribution. The audit (Phase A) is non-destructive instrumentation that distinguishes H1 from H2/H3/H4 without changing engine config; if H1 confirms, Phase B ports symmetric prompts forward.

**Why this priority**: This is the most spec-decision-heavy addition in M6.1.3 (a confirmed H1 binds M6.2 / M7 / M8 to symmetric prompts as the M6.x convention) but it's downstream of Story 1's proxy-edge attribution: the c=1 finding is on one cell only, and the c=4 / c=8 `inconclusive` cells have a *different* failure mode (proxy-edge gap, addressed by Story 1) — the root-cause investigation for c=1 doesn't bear on those cells. Audit-only instrumentation has near-zero risk and ~0 incremental Modal cost (rides on Story 1's sweep); the conditional symmetric-prompts wiring (Phase B) is invoked only if the audit confirms H1. P2 reflects "informative but narrower than P1, and decision-bearing for future milestones".

**Independent Test**: Can be fully tested by running the smoke-equivalent validation sweep (per FR-039) and confirming the resulting per-RPC sidecar JSONL (or trailing-metadata stream, format choice deferred to `/speckit-plan`) contains `tokenized_prompt_length` (integer) and `tokenized_prompt_hash` (BLAKE2b-8 hex string, 16 chars) per RPC, keyed by `(cohort, cell, iter_idx)`. A reader can compute per-cohort mean token count and per-cohort hash-distribution entropy and determine whether per-cohort distributions diverge (H1 confirmed) or are statistically identical (H1 rejected). Story 2 makes no engine-config change; the audit is purely additive instrumentation. Phase B (symmetric prompts) is invoked only if H1 confirms; until then `--m6_1_3-symmetric-prompts` defaults to off.

**Acceptance Scenarios**:

1. **Given** an M6.1.3 sweep runs any cell × cohort, **When** each RPC is dispatched, **Then** the frontend servicer captures `tokenized_prompt_length = len(token_ids)` (the integer count of token ids fed into prefill, post-`apply_chat_template` for chat_stream cohorts, post-tokenization for embed cohorts) and `tokenized_prompt_hash = blake2b(token_id_list, digest_size=8).hex()` and emits both via the same wire mechanism as the proxy-edge probes (gRPC trailing metadata + REST SSE / JSON terminal event).
2. **Given** the sweep completes, **When** the orchestrator emits the per-RPC sidecar (existing `m6_1_1` sidecar JSONL pattern), **Then** each row carries `(cohort, cell, iter_idx, tokenized_prompt_length, tokenized_prompt_hash)` so an audit-time analysis can group by cohort and compute per-cohort distributions.
3. **Given** the published artifact's reporter, **When** it generates the M6.1.3 markdown output, **Then** it includes a "Per-Cohort Prompt-Content Audit" section that renders a table of per-cohort `(mean_tokenized_prompt_length, stddev, n_rpcs, unique_hash_count)` per cell, with a one-line verdict line ("H1 confirmed: per-cohort token-count means diverge by >2σ" / "H1 rejected: per-cohort distributions statistically identical" / "H2 candidate: token-counts identical but hash distributions differ").
4. **Given** the audit reveals per-cohort token-count divergence (H1 confirmation), **When** the spec-decision logic in the reporter fires, **Then** the published markdown documents an explicit recommendation that symmetric prompts become the M6.x convention going forward, binding M6.2 / M7 / M8 spec assumptions. The recommendation cites the audit table inline.
5. **Given** the audit reveals identical per-cohort token-count means but divergent hash distributions (H2 candidate), **When** the reporter fires, **Then** the published markdown documents "encoding drift" as the leading candidate and recommends a follow-up investigation (out of scope for M6.1.3 closure). No M6.x-convention change is recommended in this case.
6. **Given** Phase B is invoked (the `--m6_1_3-symmetric-prompts` flag is set), **When** the sweep iterates cohorts for each iteration index, **Then** all cohorts receive the same logical prompt for the same iteration index (corpus-based, deterministic — using M5.2's `m5_2_symmetry` helper or an M6.x port thereof; refactoring choice deferred to `/speckit-plan`). The per-cohort token-count and token-hash distributions become identical by construction; any residual `seg_prefill` spread is then attributable to H3 / H4 / H5 rather than H1.
7. **Given** the published artifact JSON, **When** an M6.1.1-aware reader parses per-RPC sidecar rows or per-cell aggregates, **Then** the new audit fields are ignored silently — additive sidecar columns, no schema-version bump.

### User Story 3 - Characterize Between-Run Variance So Published CIs Reflect True Cohort-Comparison Uncertainty (Priority: P3)

A future operator (or M6.1.1 reader) needs to know that M6.1.1's published CIs capture only sample noise (V1) and understate true cohort-comparison uncertainty for the `chat_stream c=4` cell (noise ÷ signal ≈ 50–100%, between-run |Δ| mean 10.53 ms vs within-run spread 13–26 ms) and weakly for c=8 (noise ÷ signal ≈ 20–30%, |Δ| mean 2.69 ms vs spread 13–15 ms). The spike's analysis (`docs/spikes/m6-1-roadmap-additions/05-run-to-run-variance.md`) decomposed variance into four sources (V1 sample noise, V2 run-state noise, V3 deploy-state noise, V4 network-path noise) and showed the artifact's bootstrap CIs capture V1 only — V2/V3/V4 ride on top and compound at higher concurrency. With multi-run characterization (5 runs back-to-back at the same deploy, fixed seed, n=50), V2 becomes measurable; combined with a single n=200 power-test run, sample-size scaling for V1 becomes verifiable. The published artifact can then carry a "Between-Run Variance" block that bounds true cohort-comparison uncertainty alongside the existing CI half-widths.

**Why this priority**: This is the lowest implementation risk in the bundle — the orchestrator already supports `phase_1_runs[]` accumulation (the rehydration path landed during M6.1.1's expansion). The new code is a "run K times in sequence" wrapper, a between-run-variance compute, a new reporter section, and a new classifier label (`inconclusive_high_variance`). It carries the smallest novel surface area but is the data-volume backbone of the bundle: the 5-run multi-sweep is what produces 5 datapoints each for Stories 1 and 2 from a single Modal-deploy cycle. P3 reflects "structurally simple but operationally load-bearing".

**Independent Test**: Can be fully tested by running `--m6_1_3` (which defaults to `repeat=5` per FR-022) against a fresh Modal deploy and confirming (a) the orchestrator runs the existing Phase 1 sweep 5 times back-to-back at the same deploy (no teardown between runs), (b) each run appends to `phase_1_runs[]` in the published artifact JSON, (c) the reporter renders a "Between-Run Variance" section with per-cell per-cohort `(mean_of_means, stddev_of_means, n_runs)`, (d) the classifier upgrades any cell where between-run |Δ| exceeds a configurable fraction of within-run spread to `inconclusive_high_variance`. A reader can compare M6.1.3's c=4 between-run stddev to the within-run CI half-width to see whether the M6.1.1 verdict-uncertainty headline holds, weakens, or strengthens.

**Acceptance Scenarios**:

1. **Given** the operator launches `--m6_1_3` (defaults `repeat=5`, `n=50`), **When** the orchestrator starts, **Then** it executes the existing Phase 1 sweep (the M6.1.1-expansion classifier sweep, with Stories 1 + 2 instrumentation active) five times back-to-back at the same Modal deploy, the same `base_seed`, the same n, with no teardown between runs.
2. **Given** each Phase 1 sweep completes, **When** the orchestrator appends its result, **Then** the published artifact JSON's `phase_1_runs[]` array carries five entries, each containing the same per-cell per-cohort structure as a single-run M6.1.1 artifact (the rehydration path already supports this).
3. **Given** `phase_1_runs[]` has 5 entries (or any count ≥ 3), **When** the reporter generates the M6.1.3 markdown output, **Then** it includes a "Between-Run Variance" section with a per-cell per-cohort table containing `(mean_of_means, stddev_of_means, n_runs)`. The table is rendered only when `len(phase_1_runs) >= 3`; for shorter accumulators it is omitted entirely (the existing single-run reporter output applies).
4. **Given** a per-cell `PerSegmentAggregate` and the between-run variance for that cell, **When** the classifier evaluates its decision tree, **Then** it produces `inconclusive_high_variance` for any cell where the between-run |Δ| (max minus min of per-cohort means across runs) exceeds a configurable fraction of the within-run spread (default fraction is a `/speckit-plan` deliverable; spike-suggested starting point is ~50%, calibrated so c=4 triggers and c=1 does not based on the spike's two-run data).
5. **Given** the Phase B n=200 power test runs (single run, invoked as `--m6_1_3 --m6_1_3-diagnose-repeat=1 --m6_1_3-diagnose-n=200`), **When** the artifact is published, **Then** the per-cohort bootstrap CIs at n=200 are visibly narrower than M6.1.1's n=50 CIs by approximately `sqrt(4) = 2×`. The reporter renders a "Phase B: n=200 Power Test" comparison table alongside the multi-run variance table so a reader can see whether sample-size scaling alone closes the c=4 problem or whether V2/V3/V4 dominate.
6. **Given** the spike's analysis flagged Modal preemption as a risk for the 5-run loop (M5.2 had preemption-aware URL refresh in `m5_2_sweep.py`), **When** Modal preempts the function mid-sequence (the `*.modal.run` / `*.modal.host` tunnel returns an error or rotates), **Then** the orchestrator detects the preemption, refreshes the cohort URLs (porting M5.2's pattern), and continues the multi-run loop. The artifact records the preemption event in a per-run note but does NOT abort the multi-run accumulator.
7. **Given** Story 3's `inconclusive_high_variance` label and Story 1's `proxy_*_dominated` labels both fire for the same cell, **When** the classifier reports, **Then** it emits `inconclusive_high_variance` as the *outer* label (variance dominates attribution) with the proxy-edge attribution rendered as a parenthetical note. Stories 1 and 2's attribution machinery still runs and populates the segment columns even when Story 3 over-rides the headline label, so the published markdown carries both signals.

### Edge Cases

- **What if `time.time_ns()` and vLLM's `time.time()` are on subtly different epochs on some host?** Both are POSIX wall-clock; on Linux + macOS they return seconds (or nanoseconds) since the Unix epoch from the same `CLOCK_REALTIME` source. The spike's investigation confirmed in-process compatibility on the M6.1.1 target environment (Modal A10G eu-west-1, Python 3.11+). If a future host violates this assumption, the FR-006 negative-value assertion fires per-RPC and surfaces the platform mismatch. The harness does not silently absorb a clock-skew error.
- **What if the proxy-edge probes record a negative `seg_ingress_ms` or `seg_egress_ms` on a real production run (not synthetic)?** The wire-format assertion (FR-006) fires and the harness logs the offending RPC's raw checkpoint values for diagnosis. The single RPC's row is marked as a sanity-check failure; aggregation skips it; the sweep continues. If more than a configurable fraction of RPCs in a cell fail this check (default fraction is a `/speckit-plan` deliverable), the cell receives a `clock_anomaly` warning in its per-cell row and the classifier downgrades the cell's verdict to `inconclusive`.
- **What if the per-cohort prompt audit reveals identical per-cohort token-count means AND identical per-cohort hash distributions, yet the `engine_compute_variation` signal persists?** H1 and H2 are both rejected. The reporter recommends Phase C (engine-config probes — prefix-cache disable per H3, reversed cohort order per H4); these are out of scope for the M6.1.3 closure deliverable but documented as the next investigation step. Phase C may be invoked manually with a `/speckit-plan`-defined CLI flag, but the milestone publishes without it.
- **What if the multi-run loop hits Modal preemption between run 3 and run 4?** Per Acceptance Scenario 3.6, the orchestrator detects the preemption, refreshes URLs via the M5.2 pattern, and continues. The published artifact's `phase_1_runs[]` carries all 5 runs with a `notes` field on the preempted run that flags the URL refresh. If preemption recurs more than a configurable threshold (default `/speckit-plan` deliverable, suggested 2 in a single multi-run sequence), the orchestrator aborts the remaining runs and the reporter emits a "multi-run incomplete" warning — variance can still be computed from the runs that completed (≥ 3) but the published "Between-Run Variance" section carries an explicit `n_runs_actual < n_runs_requested` annotation.
- **What if a cohort produces no successful RPCs in one of the 5 runs (cohort-level health failure for one iteration)?** The other 4 runs' per-cohort data still aggregates; the variance compute drops the failed run's contribution for that cohort × cell only (other cohorts in the same run still aggregate). The reporter's variance table marks the affected cell × cohort with `n_runs = 4` instead of 5. If a cohort fails in 3+ of the 5 runs for the same cell, the variance compute emits `null` for that cell × cohort and the classifier emits a `cohort_unhealthy` warning.
- **What if Story 2's audit fires Phase B (symmetric prompts) and the resulting cohort-comparison is no longer directly diff-able against M6.1.1's published baseline (because M6.1.1 used the M6.1 helper's per-cohort defaulting, not M5.2-symmetric)?** The published M6.1.3 artifact explicitly carries both annotations: per-cell rows from the Phase A audit-only sweep (directly diff-able against M6.1.1, the cell-comparability property holds) AND per-cell rows from the Phase B symmetric-prompts sweep (the new M6.x baseline going forward, NOT directly diff-able against M6.1.1). The reporter renders these as two separate tables with explicit headers. A reader knows which numbers to compare against which baseline.
- **What if M6.1.2's `network_paths` probe times out on a cohort in the multi-run loop's middle run (one of the 5)?** The probe runs once per sweep (per M6.1.2's FR-001), so for the multi-run loop the probe fires once at the *first* run's start; subsequent runs reuse the captured `network_paths` block. If the first probe times out for a cohort, the FR-005 error block is captured and inherited by the remaining 4 runs' `phase_1_runs[]` entries (each run's `network_paths` references the captured block, not a fresh probe). A re-probe between runs is out of scope; M6.1.3 inherits M6.1.2's "probe once at sweep start" convention unchanged.
- **What if Story 3's `inconclusive_high_variance` label fires for a cell that previously classified cleanly under M6.1.1's single-run interpretation (e.g., the c=1 reproducible `engine_compute_variation` finding from M6.1.1 turns out to have larger between-run variance than the 2-run dataset suggested)?** The published artifact's per-cell row carries both the inner attribution (`engine_compute_variation` from the segment decomposition) AND the outer `inconclusive_high_variance` label. The reporter narrative explains that the M6.1.1 single-run finding was within-run-noise honest but multi-run uncertainty exceeded that — and recommends Phase C (multi-deploy / multi-seed) as the next investigation step if the cell's headline verdict matters for downstream operator decisions.
- **What if the multi-run loop completes successfully but Story 2's audit and Story 1's probes BOTH suggest the budget is concentrated in a single segment (e.g., 17 ms unattributed at c=4 lands ~100% in `seg_egress_ms` AND per-cohort token-count means diverge)?** Both findings are independent and the classifier emits the higher-precedence label (`proxy_egress_dominated`) with a parenthetical that the H1 prompt-content drift also contributes to the per-cohort spread. The reporter narrative addresses both signals.

## Requirements *(mandatory)*

### Functional Requirements

#### Proxy-edge probes (item #4)

- **FR-001**: The M6.1.3 sweep MUST capture two new clock-aligned checkpoints in the frontend servicers' streaming paths: `m6_1_1_t_pre_engine_wall_ns = time.time_ns()` alongside the existing `pre_engine_ns` capture, and `m6_1_1_t_first_chunk_mono_ns = time.monotonic_ns()` alongside the existing `first_chunk_ns` capture. The first provides a wall-clock anchor for comparison against vLLM's `RequestStateStats.arrival_time` (the ingress gap); the second provides a monotonic anchor for comparison against vLLM's `RequestStateStats.first_token_ts` (the egress gap).
- **FR-002**: The two new checkpoints MUST emit via the existing wire mechanisms — gRPC trailing metadata for gRPC cohorts (`default_grpc`, `tuned_grpc_multiplexed`) and the SSE / JSON terminal event for REST cohorts (`rest_https_edge`, `rest_plain_tcp`) — under the keys `m6_1_1_t_pre_engine_wall_ns` and `m6_1_1_t_first_chunk_mono_ns`. The naming uses the `m6_1_1_*` prefix (not `m6_1_3_*`) because the keys extend the M6.1.1 trailing-metadata vocabulary additively — the wire schema is shared.
- **FR-003**: The probes MUST run on streaming paths only — `CompleteStream` in `chat.py` and `CompleteStream` in `completions.py`. The unary path (`Complete`) MUST NOT emit these keys because the ingress / egress gap is a streaming-only phenomenon (`Complete` has no first-chunk-vs-engine-emit delta to bisect). For embed cohorts the existing M6.1.1 segments suffice; no probe data is emitted on those rows.
- **FR-004**: The client-side extractor (`m6_1_1_timing.py` and the REST shim's terminal-event handler) MUST read the two new keys via the existing `_opt_int` pattern (returns 0 for absent keys; the existing M6.1.1 wire-compatibility precedent) and populate two new optional fields on `TimingCheckpoint`: `pre_engine_wall_ns` and `first_chunk_mono_ns`.
- **FR-005**: The per-RPC aggregator MUST compute two new derived segments per RPC: `seg_ingress_ms = (engine_arrival_ns − pre_engine_wall_ns) × 1e-6` and `seg_egress_ms = (first_chunk_mono_ns − engine_first_token_ns) × 1e-6`. Both segments MUST be added as optional fields on `PerSegmentDelta`; the `SegmentName` Literal MUST extend to include `"seg_ingress"` and `"seg_egress"`.
- **FR-006**: Both `seg_ingress_ms` and `seg_egress_ms` MUST be `≥ 0` on every per-RPC row. The aggregator MUST fire a wire-format sanity-check assertion when a negative value is observed; the assertion logs the offending RPC's raw checkpoint values (`pre_engine_wall_ns`, `engine_arrival_ns`, `first_chunk_mono_ns`, `engine_first_token_ns`) and marks the row as a clock anomaly. Aggregation skips the offending row; the sweep continues. If more than a configurable fraction of RPCs in a cell fire the assertion (default fraction deferred to `/speckit-plan`), the cell receives a `clock_anomaly` per-cell warning and the classifier downgrades the verdict to `inconclusive`.
- **FR-007**: The per-cell `aggregate_multi_point_timings` (in `m6_1_1_sweep.py`) MUST extend `PerSegmentAggregate` to include `seg_ingress_ms` and `seg_egress_ms` columns alongside the inherited `seg_ab_ms`, `seg_queue_ms`, `seg_prefill_ms`, and any other M6.1.1-vintage segments. The aggregate mean / stddev / CI computation MUST follow the same statistical recipe as the inherited segments — no new aggregation primitive.
- **FR-008**: The M6.1.1-expansion classifier (`m6_1_1_classifier.py`) MUST extend from the 5-bucket decision tree to a 7-bucket tree by adding `proxy_ingress_dominated` (where `seg_ingress_ms` carries the dominant per-cohort spread, exceeding a configurable threshold of total `engine_ttft_ms` spread — `/speckit-plan` deliverable; spike-suggested starting point is ~40%) and `proxy_egress_dominated` (symmetric for `seg_egress_ms`). The five inherited labels (`channel_dependent_batching`, `engine_compute_variation`, `queue_dependent_batching`, `frontend_arrival_jitter`, `inconclusive`) MUST be preserved unchanged. The legacy fallback (when `seg_ingress_ms` / `seg_egress_ms` are absent — pre-M6.1.3 manifests rehydrated by the M6.1.3 reporter) MUST classify against the 5-bucket tree exactly as M6.1.1 did.
- **FR-008a**: When **two or more** attribution labels clear their per-rule dominance thresholds for the same cell, the classifier MUST apply **highest-share-wins precedence with a 5-percentage-point dominance margin**: the label whose driving segment carries the highest share of total `engine_ttft_ms` spread wins iff that share exceeds the runner-up's by ≥ 5 percentage points. If the top two are within 5 percentage points of each other, the cell MUST receive a **compound label** `multi_factor_<top>_<runner_up>` (e.g., `multi_factor_proxy_egress_engine_compute`, where `<top>` and `<runner_up>` are the abbreviated segment identifiers `proxy_ingress` / `proxy_egress` / `engine_compute` / `channel_batching` / `queue_batching` / `frontend_arrival`). Within a tied pair, the two abbreviated identifiers MUST be ordered alphabetically. The 5-percentage-point margin is the spec-level constant; the per-rule dominance thresholds (the `~40%`-of-total-spread floors per FR-008's `seg_*_dominated` rules and the equivalent thresholds for the inherited 5 buckets) remain `/speckit-plan` deliverables. The full per-cell label space therefore consists of the seven base labels, the new `inconclusive_high_variance` outer label (FR-026), and the compound `multi_factor_*` labels formed by any pair of the six driving-segment identifiers. When `inconclusive_high_variance` (FR-026) fires it remains the outer label as specified there; FR-008a's highest-share-wins / compound logic determines the *inner* label rendered as the parenthetical.
- **FR-009**: The reporter (`m6_1_1_reporter.py`) MUST render two new columns in the per-cell timing table (`seg_ingress` and `seg_egress`, formatted matching the inherited segment columns), classification narratives for the two new labels (`proxy_ingress_dominated`: "the budget lives in the proxy → engine handoff (frontend's `pre_engine` to vLLM's `arrival_time`)"; `proxy_egress_dominated`: "the budget lives in the engine → proxy yield (vLLM's `first_token_ts` to frontend's `first_chunk`)"), and a `classifier_notes` field updated to describe the 7-bucket decision tree. When a cell receives a compound label `multi_factor_<top>_<runner_up>` (FR-008a), the reporter MUST render a narrative line that enumerates the contributing segments verbatim and their respective shares of total `engine_ttft_ms` spread (e.g., `"multi-factor: seg_egress carries 45% of spread, seg_prefill carries 43% (within the 5pp dominance margin); attribution is not single-source"`). The compound-label narrative MUST cite the specific shares so the reader can judge the near-tie.
- **FR-010**: The wire schema MUST remain at `schema_version = "m6_1_1.v1"` (no version bump). The two new keys are additive at the gRPC trailing-metadata layer and SSE / JSON terminal event layer, matching the strict-superset pattern M6.1.1 itself used when adding `RequestStateStats` fields. Pre-M6.1.3 manifests parse cleanly via the extractor's `_opt_int` returning 0 for absent keys; `TimingCheckpoint.has_proxy_edge_probes` (a new computed property) returns `False`, and the classifier's legacy fallback emits a 5-bucket label.
- **FR-011**: `contracts/instrumentation.md` (or the equivalent canonical schema doc) MUST be updated to document the two new keys in the M6.1.1 wire vocabulary as the M6.1.3 addition, including the streaming-only constraint (FR-003), the negative-value assertion (FR-006), and the 7-bucket classifier extension (FR-008).

#### Per-cohort prompt-content audit (item #5)

- **FR-012**: The M6.1.3 sweep MUST capture, per RPC, the tokenized-prompt length and a BLAKE2b-8 hash of the token-id list: `tokenized_prompt_length = len(token_ids)` (the integer count of token ids fed into prefill, post-`apply_chat_template` for chat_stream cohorts and post-tokenization for embed cohorts) and `tokenized_prompt_hash = blake2b(token_id_list, digest_size=8).hex()` (16-char hex). Both values are computed on the frontend servicer side, after tokenization and chat-template application, before the request hits the engine.
- **FR-013**: The two new audit values MUST emit via the same wire mechanism as the proxy-edge probes — gRPC trailing metadata for gRPC cohorts and SSE / JSON terminal event for REST cohorts — under the keys `m6_1_3_tokenized_prompt_length` and `m6_1_3_tokenized_prompt_hash`. Unlike the proxy-edge probe keys (which use the `m6_1_1_*` prefix to extend M6.1.1's wire vocabulary), the audit keys use the `m6_1_3_*` prefix because they are a *new* category of instrumentation introduced in this milestone, not an extension of an existing vocabulary.
- **FR-014**: The audit MUST emit on **both** streaming and unary RPCs (chat_stream + embed cohorts). Unlike the proxy-edge probes (streaming-only per FR-003), prompt-content audit applies to every RPC because the H1 hypothesis (prompt-content drift) applies independent of streaming.
- **FR-015**: The orchestrator MUST emit a per-RPC sidecar row carrying `(cohort, cell, iter_idx, tokenized_prompt_length, tokenized_prompt_hash)` into the existing M6.1.1 sidecar JSONL (extending the existing per-RPC record shape). The sidecar row MUST be built by the orchestrator from the extractor's parsed `TimingCheckpoint` / per-RPC record (the same pattern the M6.1.1 sidecar already uses for `m6_1_1_*` fields) — NOT from a parallel emission path on the frontend servicer. Wire emission per FR-013 is the single canonical source of these audit values; the sidecar is the orchestrator-derived per-RPC view. The per-cell aggregate is a further derived view.
- **FR-016**: The reporter MUST generate a "Per-Cohort Prompt-Content Audit" section in the M6.1.3 published markdown, rendering per-cell per-cohort `(mean_tokenized_prompt_length, stddev, n_rpcs, unique_hash_count)`. **The per-cohort distribution per cell MUST be computed from the POOLED per-RPC audit data across all runs in `phase_1_runs[]`** (so for the milestone-publishing sweep `n_rpcs = 5 × 50 = 250` per cohort; for the validate sweep `n_rpcs = 50` per cohort). The section MUST include a one-line per-cell H1-verdict line drawn from the pooled distribution:
  - `"H1 confirmed: per-cohort token-count means diverge by >2σ"` when any pair of cohort means in a cell differs by more than 2× the pooled cohort stddev (threshold deferred to `/speckit-plan`; the criterion is the spec-level constraint).
  - `"H1 rejected: per-cohort distributions statistically identical"` when no pair exceeds the threshold AND per-cohort hash distributions are statistically identical (same Wilson-style equivalence test as the within-noise comparison the M6.1.1 reporter already uses).
  - `"H2 candidate: token-counts identical but hash distributions differ"` when per-cohort token-count means are within the threshold but per-cohort hash distributions diverge (different unique-hash sets).
- **FR-016a**: The reporter MAY render a diagnostic appendix table listing the per-run audit verdict for each cell (5 rows per cell on the publish sweep, 1 row per cell on the validate sweep) for operator-readable transparency. The appendix is NOT load-bearing for downstream spec assumptions — only the pooled-distribution headline verdict (FR-016) drives FR-017 / FR-018 recommendations. The appendix MAY be omitted when all per-run verdicts match the pooled verdict (i.e., when there's nothing to flag).
- **FR-017**: If the audit verdict on the `chat_stream c=1` cell is "H1 confirmed", the published markdown MUST carry an explicit spec-decision recommendation that **symmetric prompts become the M6.x convention going forward** (binding M6.2 / M7 / M8 spec assumptions). The recommendation MUST cite the audit table inline.
- **FR-018**: If the audit verdict on `chat_stream c=1` is "H1 rejected", the published markdown MUST recommend further investigation per Phase C of the spike's experiment design (engine-config probes — prefix-cache disable per H3, reversed cohort order per H4). The recommendation MUST flag that Phase C is out of scope for the M6.1.3 closure deliverable and provide the `/speckit-plan`-defined CLI flag for manual invocation if a follow-up operator wants to pursue it.
- **FR-019**: The M6.1.3 CLI MUST add a `--m6_1_3-symmetric-prompts` toggle flag that, when set, re-wires the sweep cohort-prompt assignment to use M5.2's `m5_2_symmetry`-style helper (same prompt for the same iteration index across cohorts; corpus-based, deterministic). Default is **off** (the M6.1.3 audit-only behaviour); the flag is invoked manually for Phase B per Story 2's design. Specific refactoring decisions (port `m5_2_symmetry.py` forward in-place, extract a shared helper, or duplicate the logic) are deferred to `/speckit-plan`.
- **FR-020**: When `--m6_1_3-symmetric-prompts` is set, the per-cohort token-count and token-hash distributions MUST be identical by construction across cohorts for the same iteration index. Any residual `seg_prefill_ms` per-cohort spread observed in a symmetric-prompts run is then attributable to H3 / H4 / H5 rather than H1 — the published Phase B markdown documents this.
- **FR-021**: The audit instrumentation MUST NOT modify the engine-config, the model, the M6.1.1-expansion classifier's decision rules, or M6.1.2's cohort definitions. The change is additive per-RPC instrumentation + new reporter section.

### Key Entities *(include if feature involves data)*

- **Proxy-Edge Probe Pair**: two new clock-aligned checkpoints emitted from the frontend servicers' streaming paths only. `m6_1_1_t_pre_engine_wall_ns` uses `time.time_ns()` (POSIX wall-clock, comparable with vLLM's `time.time()`-sourced `RequestStateStats.arrival_time`); `m6_1_1_t_first_chunk_mono_ns` uses `time.monotonic_ns()` (monotonic, comparable with vLLM's engine-core `time.monotonic()`-sourced `first_token_ts`). The engine runs in-process with the servicer so monotonic-clock cross-process caveats from vLLM source don't apply. Keys use the `m6_1_1_*` prefix because they extend the M6.1.1 wire vocabulary additively; the wire schema stays at `schema_version = "m6_1_1.v1"`.
- **Proxy-Edge Segments**: `seg_ingress_ms = (engine_arrival_ns − pre_engine_wall_ns) × 1e-6` and `seg_egress_ms = (first_chunk_mono_ns − engine_first_token_ns) × 1e-6`, computed per RPC. Both segments MUST be `≥ 0` on every per-RPC row; the negative-value assertion (FR-006) surfaces clock-source mismatches as a sanity check. Added as optional fields on `PerSegmentDelta` / `PerSegmentAggregate`; `SegmentName` Literal extends to include `"seg_ingress"` and `"seg_egress"`. Aggregated per cell × cohort the same way as the inherited segments — no new statistical primitive.
- **7-Bucket Classifier Decision Tree**: extends M6.1.1's 5-bucket tree (`channel_dependent_batching`, `engine_compute_variation`, `queue_dependent_batching`, `frontend_arrival_jitter`, `inconclusive`) by adding `proxy_ingress_dominated` (where `seg_ingress_ms` carries the dominant per-cohort spread, exceeding a configurable threshold of total `engine_ttft_ms` spread — `/speckit-plan` deliverable) and `proxy_egress_dominated` (symmetric for `seg_egress_ms`). When Story 3's `inconclusive_high_variance` also fires for the cell, that label OVERRIDES as the outer/headline verdict and the 7-bucket attribution becomes a parenthetical. Legacy fallback (when `seg_ingress_ms` / `seg_egress_ms` are absent on a rehydrated pre-M6.1.3 manifest) classifies against the 5-bucket tree unchanged. When two or more attribution labels clear their per-rule dominance thresholds, FR-008a's **highest-share-wins-with-5pp-margin** rule applies; near-ties produce a compound label `multi_factor_<top>_<runner_up>` (e.g., `multi_factor_proxy_egress_engine_compute`) with the contributing segment identifiers ordered alphabetically within tied pairs. The compound labels are first-class members of the cell-label space alongside the seven base labels and `inconclusive_high_variance`.
- **Per-Cohort Prompt-Content Audit Fields**: per-RPC `tokenized_prompt_length` (integer, count of token ids fed into prefill, post-`apply_chat_template` for chat_stream and post-tokenization for embed) and `tokenized_prompt_hash` (16-char hex, BLAKE2b-8 of the token-id list). Emitted via gRPC trailing metadata (gRPC cohorts) and SSE / JSON terminal event (REST cohorts) under the `m6_1_3_*` key prefix — a *new* category of instrumentation in this milestone, not a vocabulary extension. Applies to both streaming and unary RPCs. Sidecar JSONL carries the per-RPC tuple `(cohort, cell, iter_idx, tokenized_prompt_length, tokenized_prompt_hash)`.
- **H1 Verdict Line**: a one-line per-cell `chat_stream c=1`-focused verdict drawn from the **pooled audit data across all `phase_1_runs[]` runs** (per FR-016: pooled `n_rpcs = 5 × 50 = 250` per cohort on the publish sweep; `n_rpcs = 50` per cohort on the validate sweep) — `"H1 confirmed: per-cohort token-count means diverge by >2σ"`, `"H1 rejected: per-cohort distributions statistically identical"`, or `"H2 candidate: token-counts identical but hash distributions differ"`. The pooled-distribution headline verdict is the single load-bearing output (drives FR-017 / FR-018 spec recommendations); per-run verdicts MAY appear in a diagnostic appendix per FR-016a but do NOT drive downstream spec assumptions. If the pooled verdict is "H1 confirmed", the published markdown carries a spec-decision recommendation that symmetric prompts become the M6.x convention; if "H1 rejected", a recommendation that Phase C engine-config probes be invoked manually as a follow-up; if "H2 candidate", a recommendation that an encoding-drift investigation be opened (out of scope for M6.1.3).
- **Symmetric-Prompts Mode**: the M5.2-era cohort-prompt assignment (corpus-based, deterministic; same prompt for the same iteration index across cohorts) re-wired into the M6.1.3 sweep via the `--m6_1_3-symmetric-prompts` flag. Default is **off** (M6.1.3 ships in audit-only mode); operator invokes Phase B manually if Story 2's audit confirms H1. Refactoring choice (port `m5_2_symmetry.py` in-place, extract a shared helper, or duplicate the logic) deferred to `/speckit-plan`.
- **Multi-Run Sweep**: the existing M6.1.1-expansion Phase 1 sweep iterated N times back-to-back at the same Modal deploy, same `base_seed`, same n per cohort, no teardown between runs. Controlled by `--m6_1_3-diagnose-repeat=N` as a modifier on either `--m6_1_3` (default `N=5`, the Phase A milestone-publishing run) or `--m6_1_3-validate` (default `N=1`, the smoke-equivalent wiring check). Each run appends to `phase_1_runs[]` via the rehydration path that landed during M6.1.1's expansion (no new accumulator primitive needed). Preemption-aware per FR-028.
- **Between-Run Variance Block**: per cell × cohort `(mean_of_means_ms, stddev_of_means_ms, n_runs)` produced by `compute_between_run_variance(phase_1_runs)`. Rendered in a new "Between-Run Variance" reporter section when `len(phase_1_runs) >= 3`; omitted entirely for shorter accumulators. Stored as a top-level optional `between_run_variance` field on the `M6_1_3Run` type (name deferred to `/speckit-plan`).
- **`inconclusive_high_variance` Label**: a new classifier label fired when a cell's between-run |Δ| (max minus min of per-cohort means across runs) exceeds a configurable fraction of within-run spread (default fraction `/speckit-plan` deliverable; spike-suggested starting point ~50%). Overrides the inner attribution label as the cell's headline verdict; the inner label remains as a parenthetical so the per-cell row carries both signals.
- **n=200 Power Test**: a single Phase B sweep invoked as `--m6_1_3 --m6_1_3-diagnose-repeat=1 --m6_1_3-diagnose-n=200`, used to confirm CI half-widths shrink by ~`sqrt(4) = 2×` relative to M6.1.1's n=50 baseline. Reported in a separate "Phase B: n=200 Power Test" comparison table alongside the multi-run variance table.
- **M6.1.3 CLI Mode**: a paired set of top-level mode flags following M6.1.2's convention — `--m6_1_3` (the milestone-publishing multi-run sweep, defaults `repeat=5` + `n=50`) and `--m6_1_3-validate` (the smoke-equivalent validation sweep, defaults `repeat=1` + `n=50`) — both honoring the shared modifiers `--m6_1_3-diagnose-repeat=N`, `--m6_1_3-diagnose-n=N`, and `--m6_1_3-symmetric-prompts`, plus the `--m6_1_3-*` namespaced sub-flag family mirroring M6.1.2's CLI shape. No top-level `--m6_1_3-diagnose` flag — the `-diagnose` token is the modifier prefix only. Mutually exclusive with all M5.x / M6 / M6.1 / M6.1.1 / M6.1.2 mode flags and with each other. `--m6_1_1-diagnose`, `--m6_1_2`, `--m6_1_2-validate` semantics frozen so historical baselines stay re-runnable from the same harness commit.

## Assumptions

- The spike's read-only investigation (2026-05-17, three spike notes under `docs/spikes/m6-1-roadmap-additions/`) accurately characterized the gap, the leading hypothesis (H1 prompt-content drift), and the variance decomposition (V1 sample / V2 run-state / V3 deploy-state / V4 network-path). Specifically: vLLM's engine-core monotonic timestamps come from `time.monotonic()` (per `vllm/v1/engine/__init__.py:149-153`) and the engine runs in-process with the frontend servicer, so cross-process monotonic-clock caveats do not apply.
- The M6.1.1 published numbers (Run 2 from `docs/benchmarks/m6_1_1-engine-cost-instrumentation.md`) are the comparison baseline: `chat_stream c=4` unattributed ~17 ms of 26 ms total spread (64%), `chat_stream c=8` unattributed ~5 ms of 13 ms total spread (37%), `chat_stream c=1` reproducible `engine_compute_variation` (`default_grpc` ~5–6 ms slower than the other two cohorts). Spike #6's two-run between-run analysis (mean |Δ| 0.37 ms at c=1, 10.53 ms at c=4, 2.69 ms at c=8) is the variance-characterization baseline.
- M6.1.2 has landed before M6.1.3 starts implementation (per PLAN.md ordering). The 4-cohort matrix, `network_paths` block, `cohort_set` + optional `cohort_omissions` metadata, and timestamped progress lines are M6.1.3's harness defaults. M6.1.3 does not modify any of those conventions.
- The M5.2 `m5_2_symmetry.py` helper is in-tree and recoverable for Phase B's symmetric-prompts wiring. Specific refactoring decisions (port forward in-place, extract a shared helper, duplicate the logic into an `m6_1_3_symmetry.py`) deferred to `/speckit-plan`.
- The M6.1.1-expansion classifier's 5-bucket decision tree, the `phase_1_runs[]` rehydration accumulator, the segment-decomposition + `engine_cost_drift_warning` machinery, and the M6.0a-corrected concurrent dispatch are all in place and accommodate M6.1.3's additions without architectural change. The classifier's 5→7 extension is a decision-tree extension, not a re-design.
- Modal's tunnel rotation cadence is slow enough that 5 back-to-back runs at n=50 (~75 min total) typically complete without preemption. FR-028's preemption-aware URL refresh is the safety net; the M5.2 pattern is presumed portable to `m6_1_1_diagnose.py`.
- The audit's BLAKE2b-8 hash on the token-id list is sufficient to distinguish H1 (different prompts) from H2 (same text, different tokenization) — collision probability at 64 bits over the expected per-cell RPC volume (50 RPCs × 4 cohorts = 200 hashes per cell, 6 cells = 1200 hashes per sweep) is negligible. Hash-length tuning out of scope.
- vLLM's `RequestStateStats.arrival_time` is a wall-clock value comparable with the frontend's `time.time_ns()` capture on the same in-process Python runtime. The spike's source-read at `vllm/v1/metrics/stats.py:202-217` confirms this; the M6.1.3 spec presumes the relationship holds across Modal Python runtime updates (a presumption that the FR-006 negative-value assertion guards).
- The negative-value assertion (FR-006) is the canary for any future change to vLLM's clock-source choices. If a future vLLM version switches `arrival_time` from `time.time()` to `time.monotonic()` (or vice versa for `first_token_ts`), the assertion would fire on every RPC and M6.1.3's instrumentation would need an upstream-aware shim. Out of scope for this milestone.
- M6.1.3 follows the M6.0a precedent for verbatim preservation of prior-milestone audit artifacts — no edits to M6 / M6.1 / M6.1.1 / M6.1.2 published bodies; the single exception is the optional forward-pointing annotation on M6.1.1's published markdown per FR-031 / FR-038 / PLAN.md.
- M6.2 depends on M6.1.3's resolved verdicts (the `max_tokens` axis's null anchors validate against M6.1.3's attributable Phase 1 baseline, not M6.1.1's `inconclusive` placeholders). The milestone ordering is presumed unchanged.
- The Phase B n=200 power test exists primarily to verify CI half-widths shrink as `1/√n` predicts, not to publish new per-cell verdicts (the published verdict baseline remains the Phase A n=50 5-run multi-sweep). If Phase B reveals systematic deviation from `1/√n` scaling, M6.1.3 documents the finding in the Phase B sibling artifact (FR-045) but does NOT swap the Phase A baseline.
- Phase B is conditional on the Phase A variance signal per FR-043 — the spec presumes that the c=4 cell will typically trigger the conditional (consistent with spike #6's two-run data showing chat_stream c=4 noise ÷ signal ≈ 50–100%) so the milestone-publishing operator should plan for the ~$2.90 cost case rather than the ~$1.74 case, and reserve the ~$1.74 case for the genuinely-clean Phase A outcome.
- The configurable thresholds named in FR-006 (negative-value assertion fraction), FR-008 (proxy-edge dominance threshold), FR-016 (H1 confirmation 2σ threshold), and FR-026 (high-variance threshold) are all deferred to `/speckit-plan` for literal-value resolution. The spec-level constraints are the criteria; the numeric tuning is a planning deliverable.
